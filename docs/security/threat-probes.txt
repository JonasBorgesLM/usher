Reading this run: every T-nn in docs/THREAT-MODEL.md has either a passing
probe or an explicit GAP line saying why it has none, per §6's own
verification rule. All 21 threats are accounted for; nothing is silent.

Five GAPs, in two different categories:

- T-08 and T-13 each have a real, passing probe for their non-gateway half
  (the resource server's own independent defense, RS-18/RI-04) plus a GAP
  for their gateway half. T-17 is entirely about the gateway. All three GAPs
  share one root cause: internal/proxy.NewHandler is built and unit-tested
  (#40-#42) but was never wired into cmd/usher/main.go when this script was
  written, so there is no live /api/** route to send a request through.
  Filed as #104; closing it turns these three GAPs into probes, not a
  rewrite of this script.
- T-18 and T-19 are GAPs by design, not by gap in coverage: no HTTP
  endpoint can answer "did the mounted keyset leak" or "did an audit event
  reach crier" from outside, so no probe for either will ever exist here.
  §6 calls this out explicitly rather than asking for one.

Two bugs were found and fixed while building this script, not by it:

- cmd/usher/main.go's loginLimiter and authorizeLimiter shared one Redis
  key function (the client's bare IP) despite being configured with
  different (burst, perSecond) tiers -- moat/ratelimit.Store.TakeN keys
  purely by that string, so the two limiters collided on one bucket.
  Confirmed live: six requests to /consent alone drove /authorize's own
  reported Remaining from 19 to 0. Fixed with namespacedKeyFunc
  (cmd/usher/main.go), regression-tested in cmd/usher/main_test.go with a
  negative control seen failing before the fix.
- scripts/timing-login's own sibling, check-readme-examples.sh, is
  unrelated; the bug here was in this script's own early draft, not in
  product code: an &#43; entity in a CSP nonce's HTML attribute (html/
  template correctly escaping a base64 '+') was compared byte-for-byte
  against the un-escaped CSP header value. Fixed by decoding that one
  entity before comparing, in probe_t21.

T-01's own probe (replaying an already-consumed code) revokes the whole
refresh-token family that code minted -- RS-04's own "replay revokes"
mitigation, working as intended, not a bug. It runs after T-07 and T-20 in
this script's own call order for exactly that reason: both still needed
REFRESH_TOKEN from the same shared grant.

loginLimiter's burst (5) and refill rate (1/s) are tight by design (RS-22).
A few probes drive dedicated login/consent flows of their own on top of the
shared setup's, so this script paces itself with short sleeps before them
rather than racing a limiter that is correctly strict -- the same thing a
well-behaved real client would have to do.

A re-run without clearing anything by hand passes the same way: the shared
setup's own authorize_login_consent helper treats "session already
authenticated" and "consent already granted" as 303s to follow, not errors,
so this script tolerates being run against a stack it already drove once.
