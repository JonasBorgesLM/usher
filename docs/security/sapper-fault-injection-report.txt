---

Reading this run: the scenario's injector (fault_kind: drop) sits between
usher's gateway and the real resource-server, forwarding cleanly during
the before/after phases and aborting the connection (http.ErrAbortHandler)
during the 20s faulted phase -- the one fault_kind that produces a genuine
Go transport error, since bastion's isFailure classifier (bastion/breaker.go)
only ever sees an error, never an HTTP status code; fault_kind: error (a
direct status response) would never reach usher's breaker at all.

A parallel second-by-second curl probe against GET /api/widgets (outside
sapper's own load, using a fresh token) shows the exact transition live:

  1s  502   (dial refused -- injector not listening yet; RS-20 holds: no
             upstream host/port/stack trace in the body, Content-Length: 0)
  2s  502
  3s  503   retry-after=30   <- bastion.Breaker opened (5 consecutive
                                 failures: 2 manual probes + the watcher's
                                 own + early load before the injector came
                                 up) -- RI-02 rule 1: 503+Retry-After, never
                                 a bare 502 or 500, once the breaker itself
                                 is why the call didn't go through
  4s..31s  503  retry-after=30   (holds for the breaker's openTimeout)
  32s  200                   <- half-open probe succeeded; breaker closed
  33s..46s  200               (the run's own 40s "after" baseline)
  47s..70s  503  retry-after=30  (the SAME run's own faulted phase starts
                                   its own 20s window -- confirms the
                                   breaker is the one documented in RI-02 as
                                   process-global, "one named breaker per
                                   upstream," not scoped to one caller or
                                   one sapper run: the author's own manual
                                   curl probes and sapper's load share and
                                   drive the identical breaker state)

A final check well after the run ended (nothing listening on
profile.listen any more, the sapper process having exited and its injector
with it) returns 502, not 503 -- confirming the breaker itself had already
closed again by then; what is reachable now is a genuinely absent
dependency, not a tripped circuit. The two status codes stay distinguishable
exactly as RI-02 rule 1 requires.

This closes issue #54's second done-when item ("upstream fault opens the
breaker, sheds, recovers") for real, against usher's own gateway and real
resource-server, not sapper's own internal test fixture. T-17's own GAP in
scripts/probe-threats.sh is updated to cite this file instead of claiming
the threat is unprobeable -- it is probeable, just not from a single
sequential black-box HTTP script the way T-01..T-16 are: it needs a second,
correlated traffic stream (sapper's own load) and a target reconfigured for
the run's duration, which is exactly what this evidence captures instead.

Residual, stated plainly: this is a recorded run, re-run manually, not a
CI gate the way scripts/probe-threats.sh is. A regression in the breaker's
wiring (cmd/usher/router.go) would not fail a build on its own; only a
repeat of this procedure would catch it. Automating it (wiring this
scenario into CI, with the docker-compose override and token exchange
scripted) is future work, not done here.
