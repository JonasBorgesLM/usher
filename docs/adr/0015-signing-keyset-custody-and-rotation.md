# ADR-0015: Signing keys are a mounted keyset with explicit publication and signing windows

## Status
Proposed — 2026-09-29

## Context
RS-09 requires rotation without downtime: a key is published before it signs,
and stays published after it stops signing for
`max_access_token_TTL + clock_skew + consumer_JWKS_cache_TTL`. REQUIREMENTS §7.1
keeps private keys out of the database ("mounted file or KMS"). v0.3 did not say
how several instances agree on which key signs now, how a new key arrives, or
what happens when one leaks.

## Decision (proposed)
- Keys are files in a mounted directory, one per key, each with a small
  metadata file: `kid`, algorithm, `publish_at`, `sign_from`, `retire_at`.
- Every instance derives the JWKS and the active signing key from the keyset
  and the clock alone — no runtime coordination. The key whose `sign_from` is
  the latest one not in the future signs.
- At load, usher refuses a keyset where the active key's `publish_at` is not at
  least `consumer_JWKS_cache_TTL` before its `sign_from`, or where a retiring
  key's `retire_at` is closer than RS-09's formula after the next key's
  `sign_from` (RNF-05).
- Rotation is an operator action: add the next key with future timestamps; no
  restart needed if the keyset is re-read periodically.
- Phase 2 uses a keyset with a single key; phase 3 adds the schedule.

## The alternative that was rejected
**Keys generated by usher and stored encrypted in Postgres.** Automatic
rotation and one source of truth across instances. Rejected in this proposal
because it puts key material in the store a SQL injection or a dump reaches,
and the encryption key has to live somewhere — back to the mounted file.

**A KMS signing API.** The right answer for production (keys never leave the
KMS), and the wrong dependency for a local, `docker compose up` study project.

## Consequences
- Clock skew between instances can make two keys sign briefly; both are
  published, so both verify. Harmless, and tested.
- Emergency revocation of a leaked key is removing it from the keyset, and the
  exposure lasts until every consumer's JWKS cache expires (T-18's residual).

## Open questions — why this is Proposed
1. Is there an emergency path shorter than the JWKS cache TTL — for example, a
   `kid` denylist pushed to the gateway, accepting that direct consumers do not
   see it (the same shape as ADR-0014)?
2. Periodic re-read of the keyset versus restart-to-rotate.
3. RS256 or ES256 as the default algorithm (RS-06 allows both).

Accept, with the answers, before phase 2 starts.
